The problem

Finding misconfigurations is easy. Proving the answer is not.

A startup closes its first enterprise customer, and a security questionnaire arrives. Do all IAM users have MFA? Is data encrypted at rest? Prove it.

There is no compliance team — just a two-year-old AWS account nobody has fully audited and a deal waiting on the answers. Plenty of scanners will list what is wrong. None of them will tell an auditor how you know, or when you checked, or what happens the next time something drifts.

An auditor does not want a dashboard. They want the observation, the timestamp, and the chain back to the API that produced it.

Why it is an agent, not a scanner

The catalog says which controls matter. It never says what to call.

One report, two verdicts.

Nothing in the codebase iterates the catalog to “run the sweep.” The agent reads it and decides what to fetch, in what order, and when one result has already answered a second control.

In this run it worked out that the IAM credential report settles both MFA coverage and key rotation — and did not fetch it twice. That inference is not scripted anywhere.

An error is not a pass.

One seeded bucket denies permission to read its encryption configuration. The tool returns null with an error code rather than raising, and the agent has to decide what that means.

Not PASS, which would be a false assurance an auditor eventually catches. Not FAIL, which would be a finding nobody observed. Not a crash. That judgment is the product, and it is not expressible as a fixed sequence of API calls.

The security model

Two places where control leaves the model.

A model saying “the user approved this” is not authorization. Both boundaries are enforced in code, in the tool body — never delegated to the system prompt.

Verified against a live account

No approval, a pending approval, an approval replayed from a different bucket, and an approved-but-out-of-scope resource were each refused with the bucket confirmed unchanged. The correctly bound approval applied, verified itself, and was burned so it could not authorize a second write.

The moment it earns trust

It asks, you decide, it verifies its own work.

01

It finds the gap

A bucket encrypts with SSE-S3, not a customer-managed key — which is what enterprise reviews actually ask for.

02

It asks, in plain language

A pending approval, bound to that one action on that one bucket, expiring in 24 hours. It does not wait or poll — it records the failing verdict and moves on.

03

You approve

The decision is read from the record, never from the caller. A crafted request cannot assert that something was approved.

04

It applies, then re-reads

The verdict flips on what it observes afterwards — not on the write having been attempted.

What running it for real found

Every serious bug lived between two correct layers.

Unit tests on either side passed throughout. Each was only visible by exercising the whole path with the values a real caller would use.

A verdict could cite evidence that did not exist

record_finding checked that the citation list was non-empty — never that the ids were real. A hallucinated id would have been stored looking fully substantiated. For a tool whose entire pitch is traceability, that is the worst available failure.

→ citations validated against what the run archived

An empty sweep was filed as complete

A content filter truncated the model's output mid-answer and the run was recorded COMPLETE with zero verdicts. For a compliance tool that reads as “we checked and found nothing wrong.”

→ a sweep that records nothing is now FAILED, explicitly

That empty run then became the drift baseline

Which made every control look new, and would have hidden a regression — the one thing drift exists to surface.

→ a baseline must have recorded verdicts

The agent would have addressed a bucket that does not exist

Redaction scrubs the account id even from demo names, so the agent saw one name while S3 knew another. Every guard would have reported success right up to the write, which would have failed with NoSuchBucket — live, during the demo.

→ names resolved at the two points they meet AWS

Real names reached the trust packet three ways

Through lists of bare strings, through the resume message, and through the remediation tool's own return value. Each time the model wrote the real name into its rationale, and from there it reached the published artifact.

→ redaction applied to every tool whose result reaches the model

An unencrypted S3 bucket cannot exist any more

The planned demo was finding one and encrypting it. Since 2023 S3 applies AES256 as an unremovable baseline. The control was retargeted to test encryption strength — which is what enterprise reviews ask, and makes the agent distinguish an AWS-managed key from a customer-managed one.

→ a better control than the one originally planned

A single Strands agent running Claude Sonnet 4.5 on Bedrock: ten read-only evidence tools, eight control-flow tools, and one approval-gated remediation tool. A sliding window caps context across a long sweep.

State lives in DynamoDB — runs, controls, evidence, approvals with a TTL, and an append-only audit log. Evidence and packets go to S3. The agent is runtime-agnostic: it does not know whether the CLI, a container, Lambda or AgentCore invoked it, and a test enforces that.

Why it matters

A prompt asking a model to behave is not a security control.

Attest is built on the assumption that the agent will sometimes be wrong — and that being wrong must be survivable. Reads cannot write. Writes need a human decision the model cannot manufacture. Identities never reach the model at all. And every verdict carries the observation that produced it, so a reader never has to take the agent's word for anything.

That is what makes the output worth handing to an auditor: not that the agent is reliable, but that you do not need it to be.
